## 1. 요약

**서비스 한 줄 정의.** 콜비는 "한 줄로 맡기면 장소를 찾아 대신 전화하고, 웹에서 할 일을 함께 처리하며, 중요한 순간에만 내게 묻고, 결과를 일정·지도·공유로 이어 주는 한국어 개인 비서"다.

**목표 사용자.** 전화로만 되는 일(예약·변경·취소·문의·협상)을 미루거나 부담스러워하는 한국어 사용자를 1차 대상으로 한다. 이 가운데 바쁜 직장인, ARS와 고객센터를 어려워하는 중장년, 출석·쿠폰 같은 혜택을 챙기는 사용자, 가족 일정을 관리하는 사용자를 대표 집단으로 둔다(§3, 모두 가정).

**핵심 가치 3가지.**

1. **전화로만 되는 일을 끝내 준다.** 한국어·한국 전화망에서 발신해 목적을 달성하는 서비스는 빅테크와 국내 통신사 모두 내놓지 않았다(01 §1-1·2, 01 §5.1). 콜비는 이미 실제 070 발신과 통화 중 승인을 갖추고 있다(README).
2. **맡기되 통제한다.** 돈·약정·발송·제출·로그인 직전에만 멈추고, 승인에 "N원까지" 같은 조건을 달 수 있으며, 답이 없으면 진행하지 않는다. 업계 표준 확인 규칙과 같은 방향이면서(01 §1-3, 01 §7.2), "한 줄 조건을 단 통화 중 승인"은 조사한 서비스에서 확인되지 않은 차별점이다(01 §7.1-1).
3. **결과가 다음 일로 이어진다.** 결과는 "확인된 것 / 확인 못 한 것 / 다음 할 일"로 나누어 보여 주고(02 §5 P18), 캘린더 추가·길찾기·카카오톡 공유로 바로 이어 준다(02 §5 P19, 02 §6).

**출시 범위.** 상용 첫 출시(Phase 1 MVP)는 "전화 비서의 완성"에 집중한다. 계정·푸시·다중 인스턴스 같은 배포 선행 과제를 Phase 0에서 먼저 해소한 뒤, 한 줄 부탁(받아쓰기 포함) → 카카오 로컬 기반 장소 찾기 → 계획 확인 → 실제 통화 → 앱 밖 승인 알림과 잠금 화면 진행 표시 → 결과와 후속 행동(기기 캘린더, 지도 앱, 공유)까지를 하나의 "작업" 흐름으로 제공한다. 출석 이벤트는 자동 참여가 아니라 마감 알림과 사이트 바로 열기로 시작한다(01 §6.2, 01 §7.3-1). 웹 작업(손 넘기기 포함), Google Calendar·Gmail 연동, 여러 곳 비교 통화, 기억 카드는 Phase 2에, 메일 초안·대화형 음성·통화 넘겨받기 같은 확장은 Phase 3에 둔다.

**디자인 검토 반영(2026-11-26, 06).** 제품 경험의 중심을 Today 대시보드 · 음성 우선 비서 · 업무 실행 관리 세 가지로 정했다. 앱은 오늘 / 업무 / (가운데) 비서 / 기록 / 내 정보의 5칸 탭으로 구성하고, 오늘의 브리핑·일정은 Phase 2에, AI 비서 화면과 업무 실행 단계 화면은 Phase 1에 넣는다(§4.17, §5).

## 2. 서비스 콘셉트

### 2.1 비서의 성격

| 항목 | 정의 |
|---|---|
| 말투 | 해요체, 쉬운 말, 한 화면 한 메시지. 화면 문구와 통화 음성이 같은 사람처럼 들리게 한다(02 §6, 02 §8.1-6, EPIC D11) |
| 태도 | 할 수 있는 일과 없는 일을 먼저 밝힌다(02 §4.4 HAX G1·G2). 잘 모르면 확정처럼 말하지 않는다(EPIC D5) |
| 상대방에 대한 예절 | 통화 첫마디에 AI 비서임과 사용자를 대신해 건다는 사실을 밝힌다(01 §3.2 Call for Me, EPIC INTAKE OD-7). 짧고 정중하게 용건을 말한다(01 §7.3-4) |
| 실행 방식 | 사용자의 목적을 하나의 "작업"으로 받고, 전화·웹·연동은 작업 안의 실행 수단으로 다룬다(02 §3.11, 02 §7.2 C2) |

### 2.2 약속 — 하는 일과 하지 않는 일

| 콜비가 하는 일 | 콜비가 하지 않는 일 |
|---|---|
| 사용자가 확인한 정보만 상대에게 전달한다(02 §3.2, 02 §5 P7) | 사람인 척 통화하지 않는다(01 §7.3-4) |
| 돈·약정·발송·제출 직전에 묻고, 답이 없으면 진행하지 않는다(만료 = 거절, EPIC D4) | 비밀번호·카드번호·주민번호를 받거나 보관하지 않는다. 로그인과 결제 정보 입력은 사용자가 직접 한다(01 §6.3, 02 §5 P15) |
| 확인 못 한 결과는 "확인 못 함"으로 표시한다(EPIC D5, 02 §7.1) | 사용자 몰래 정기적으로 로그인하거나 출석을 자동 처리하지 않는다(01 §6.2, 01 §7.3-1) |
| 작업 기록과 기억을 사용자가 보고 지울 수 있게 한다(02 §1-9, 02 §8.1-5) | Captcha 우회, IP 바꾸기 같은 탐지 회피를 하지 않는다(01 §6.2, 01 §7.3-2) |
| 온라인 예약이 되는 곳은 해당 플랫폼으로 안내한다(01 §7.1-3) | 장소 검색 결과로 자체 업체 DB를 만들지 않는다(01 §6.4, 01 §7.3-3) |
| 웹 페이지·메일 속 문장을 지시로 따르지 않는다(01 §6.3) | 긴급·특수번호에 걸지 않는다(OPERATIONS "발신 번호 정책") |

### 2.3 자율성 단계

출시 때 사용자가 고르는 단계는 두 개로 제한한다(02 §5 P17). "제안만"은 사용자가 고르는 단계가 아니라 반복·알림 작업의 고정 동작이다.

| 단계 | 이름(화면 표기안) | 동작 | 적용 범위 | 출시 |
|---|---|---|---|---|
| L0 | 제안만 | 실행하지 않고 알림과 바로가기만 준다 | 출석·이벤트 마감 알림(F-ROUT-01), 반복 작업 실행 전 알림(F-ROUT-04) | Phase 1 |
| L1 | **묻고 하기(기본값)** | 계획 카드를 보여 주고 [이대로 시작]을 한 번 누르면 실행한다(EPIC §1 소유자 결정 3) | 모든 작업 | 보유 |
| L2 | 알아서 하기(저위험만) | 계획 카드를 건너뛰고 바로 실행한 뒤 결과만 보고한다 | 영업시간·재고·가격 확인처럼 정보만 묻는 전화, 그리고 사용자가 이미 고른 장소에 한정 | Phase 2(F-SET-01) |

L2 허용 여부와 범위는 소유자 결정 사항이다(§14 OD-7).

### 2.4 반드시 사용자 확인을 받는 지점

자율성 단계와 관계없이 아래 지점에서는 항상 멈춘다. 이 규칙은 전화·웹·연동에 똑같이 적용한다(01 §1-3, 01 §7.2, 로드맵 §8 원칙 1).

| # | 지점 | 확인 방식 | 근거 |
|---|---|---|---|
| C-1 | 돈이 나가는 결정(예약금, 수수료, 유료 옵션) | 승인 카드, 금액 상한 칩("N원까지") | 01 §6.3, 02 §5 P14 |
| C-2 | 약정·해지·계약 조건 변경 | 승인 카드 + 조건 코멘트 | EPIC D4 |
| C-3 | 예약 확정·변경·취소 | 승인 카드(통화), 제출 확인(웹) | 01 §3.3 Gemini, Copilot |
| C-4 | 웹 양식 제출, 메일 발송, 게시 | 지켜보기 모드에서 사용자가 직접 누름 | 01 §3.3, 02 §5 P16 |
| C-5 | 로그인, 결제 정보 입력, Captcha, 본인 인증 | 손 넘기기(사용자가 직접 조작, 그동안 기록 중지) | 01 §6.3, 02 §5 P15 |
| C-6 | 계획 카드에 없던 개인 정보를 상대에게 추가로 알려야 할 때 | 승인 카드 | 02 §5 P7 |
| C-7 | 캘린더·메일 등 연결한 앱에 쓰기 | 쓰기 전 확인 시트 | 로드맵 §4.2 커넥터 원칙, 02 §5 P19 |
| C-8 | 반복 작업의 매회 실행 | 실행 전 알림 → 승인 | 01 §1-9, 01 §3.3 Gemini 경고 |

보조 규칙:

- **거래마다 따로 묻는다.** "지난번에 승인했으니"를 자동 승인 근거로 쓰지 않는다(01 §7.2, 01 §3.3 ChatGPT 결제).
- **만료 = 거절.** 제한 시간 안에 답이 없으면 진행하지 않는다(EPIC D4).
- **코멘트는 정책을 넘지 못한다.** 카드번호·비밀번호를 코멘트로 넘길 수 없고, 승인 범위를 넘는 약정은 할 수 없다(EPIC D4, APPROVAL OD-1).

## 4. 기능 목록

### 4.1 표기

- **위험도**: 높음(돈·법·계정 제재·개인정보 노출 가능), 중간(오작동 시 사용자 불편·신뢰 손상), 낮음.
- **우선순위**: P0(출시에 없으면 상용 서비스가 성립하지 않음), P1(경쟁력·확장의 핵심, 출시 후 바로 다음), P2(검증 후 확장), 제외(제공하지 않기로 한 항목).
- **출시 단계**: 보유(현재 구현됨, 필요하면 개선), Ph0~Ph3(§11).
- 기능 ID는 디자인 문서와 SPEC이 참조하므로 바꾸지 않는다. 삭제할 때는 번호를 비워 둔다.

### 5.1 내비게이션 후보 비교와 확정

02 §8.2의 세 후보를 이 문서의 기능 범위에 비추어 다시 비교했다.

| 기준 | A. 부탁 홈 + 작업함(3탭) | B. 대화 홈(2탭 + 작업 카드) | C. 4탭 확장형(장소 탭 추가) |
|---|---|---|---|
| 기본 화면 안정성 | 부탁 입력을 처음부터 고정한다 | 대화 흐름이 기본 화면이 된다 | 부탁 입력 유지 |
| 진행 중·내 차례 작업 찾기 | 작업함 "내 차례" 묶음과 배지로 분명하다 | 대화에 묻힌다(02 §8.2) | A와 같음 |
| 웹·반복·연동 확장 수용 | 작업 종류만 늘리면 된다 | 대화 안 카드 종류가 늘어 복잡해진다 | A와 같음 |
| 장소 기능 | 홈 입력과 장소 후보 화면으로 처리 | 대화 안에서 처리 | 별도 탭. 검색 품질이 네이버·카카오에 못 미치면 빈 탭(02 §8.2) |
| 구현 범위 | 현재 구조 확장(02 §8.2) | 가장 큼 | 중간 |
| 플랫폼 권고 | 탭 3개, 권장 범위 안(02 §4.2) | 2탭 + 상단 버튼 | 4탭 |

> **2026-11-26 개정(06 DR-2·DR-4).** 아래 A안 확정은 디자인 검토(05 §4)와 승인된 목업에 따라 다음과 같이 바뀌었다. 아래의 원래 비교와 이유는 기록으로 남긴다.
>
> **확정(개정): 5칸 하단 탭 — 오늘 / 업무 / (가운데) 비서 / 기록 / 내 정보.** 가운데 비서는 탭이 아니라 어느 화면에서든 AI 비서(SCR-A01)를 여는 버튼이다. 부탁 흐름은 홈 안에 카드를 쌓지 않고 AI 비서 → 장소 선택 → 계획 확인 → 업무 실행으로 화면을 넘긴다. 끝난 업무는 기록 탭으로 옮겨, 업무 탭은 "지금 챙길 일"만 보인다.
>
> A안의 이유 1(내 차례를 놓치지 않음)과 3(실행 수단으로 탭을 나누지 않음)은 그대로 지킨다. 탭 배지는 업무 탭에만 두고, 장소 탭은 여전히 두지 않는다. 이유 2(기본 화면 고정)는 기본 화면을 "부탁 입력"에서 "오늘"로 바꾸되, 출시 때부터 고정한다는 뜻은 유지한다. 탭이 다섯 칸이 되는 것은 02 §4.2의 권장 범위(3~5개) 안이다.

**(원래 결정) 확정: A안(3탭: 홈 / 작업함 / 내 정보)을 채택하고, 홈에서 부탁한 직후의 화면은 B안처럼 "카드가 쌓이는 흐름"(장소 후보 → 계획 카드 → 진행 카드)으로 보여 주는 혼합형으로 한다(02 §8.2 권고).**

이유:

1. 출시 주력이 전화 대행이고, 승인·손 넘기기처럼 "내 차례"를 놓치지 않는 것이 핵심이다. 작업함 맨 위 "내 차례" 묶음과 탭 배지가 이 요구에 가장 직접 답한다(02 §5 P20).
2. 기본 화면(부탁 입력)을 출시 때부터 고정해, 이후 탭을 더해도 사용자가 매일 보는 화면이 바뀌지 않는다(02 §3.9 카카오톡 친구탭 교훈, 02 §6).
3. 실행 수단(전화·웹·연동)으로 탭을 나누지 않는다(02 §3.11 배민 탭 통합). 장소는 탭이 아니라 작업의 한 단계다. 장소 탭(C)은 검색 제휴가 확보된 뒤 선택지로 검토한다.

## 6. 핵심 사용자 흐름

### 흐름 1. 한 줄 부탁 → 장소 찾기 → 계획 확인 → 통화 → 승인 → 결과

1. 사용자가 홈(SCR-H01)에 "강남역 파스타집 금요일 7시 2명 예약해 줘"를 입력하거나 받아쓰기로 말한다(F-REQ-01·02).
2. 서버가 부탁을 해석한다. 대상이 장소 조건뿐이면 카카오 로컬을 실시간 호출해 후보를 만든다(F-PLACE-01). 검색 결과는 저장하지 않는다.
3. 장소 후보(SCR-H02)에서 사용자가 한 곳을 고른다. 위치 조건이 "근처"면 이때 처음 위치 권한을 묻는다(F-PLACE-03).
4. 계획 카드(SCR-H04)가 확인이 필요한 칸만 펼쳐 보여 준다. 번호 출처("검색 결과", "지난번 통화한 번호")를 붙인다. 시작 버튼 위에 예상 소요 시간을 적는다(F-NOTI-05).
5. 첫 작업이면 [이대로 시작]을 누르는 순간 알림 권한을 사전 안내(버튼 하나)와 함께 요청한다(02 §5 P24).
6. 작업 상세(SCR-T02)로 넘어가고 잠금 화면 진행 표시가 시작된다(F-NOTI-03). 서버는 발신 직전 번호 정책·수신 거부 목록을 다시 확인한다(F-CALL-09, EPIC D3).
7. 상대가 받으면 AI 고지 첫인사로 시작한다(F-TRUST-01).
8. 예약금이 필요하다는 말이 나오면 AI가 상대에게 잠시 기다려 달라고 하고 승인을 요청한다. 앱이 닫혀 있으면 긴급 알림이 간다(F-NOTI-02).
9. 사용자는 승인 카드에서 "1만 원까지" 칩을 누르거나 조건을 적어 승인한다(F-APPR-03·04). 제한 시간이 지나면 거절로 처리하고 AI는 "확인 후 다시 연락드리겠다"고 마무리한다(F-APPR-02).
10. 통화가 끝나면 결과 정리 후 결과 카드(SCR-T05)를 보여 주고 완료 알림을 보낸다. 잠금 화면 진행 표시는 바로 종료한다.
11. 주 행동 [캘린더에 추가]를 누르면 확인 시트(SCR-T06)를 거쳐 기기 캘린더에 쓴다(F-INTG-02). [길찾기]는 기본 지도 앱으로 넘긴다(F-INTG-04).
12. 예외: 상대가 AI라서 끊으면 F-CALL-10에 따라 "직접 걸기 / 다른 곳 찾기"를 제안한다. 통화 연결 실패는 F-RES-07로 다음 길을 준다.

### 흐름 2. 웹 작업과 손 넘기기(Phase 2)

1. 사용자가 "구청 체육관 다음 달 둘째 주 토요일 오전 대관 신청해 줘"를 입력한다.
2. 서버가 웹 작업으로 분류하고, 대상 사이트가 허용 목록에 있는지 확인한다(F-WEB-02). 없으면 "아직 이 사이트는 맡을 수 없어요"와 사이트 바로 열기를 준다.
3. 계획 카드에 단계(사이트 열기 → 로그인(직접) → 신청서 작성 → 제출 직전 확인)와 상대 사이트에 입력할 정보를 보여 준다.
4. [이대로 시작] 후 웹 작업 화면(SCR-T03)이 열리고 AI 조작 표시 띠와 행동 기록이 나타난다(F-WEB-03). 사용자가 앱을 떠나면 작업을 멈추고 "돌아오면 이어서 할게요" 알림을 보낸다.
5. 로그인·본인 인증 화면에 닿으면 손 넘기기(SCR-T04)로 바뀐다. 이유, "지금 화면은 기록하지 않아요", 남은 시간, [다 했어요, 이어서]를 보여 준다(F-APPR-06). 앱이 백그라운드면 긴급 알림을 보낸다.
6. 사용자가 인증을 마치고 [다 했어요, 이어서]를 누르면 AI가 다시 조작한다. 남은 시간이 지나면 작업을 멈추고 "내 차례"에 남긴다.
7. 신청서를 채운 뒤 제출 직전에 멈추고, 입력 내용 요약과 함께 사용자가 직접 [제출]을 누르게 한다(F-APPR-07, C-4).
8. 접수 완료 화면의 스크린숏과 접수 번호를 결과 카드에 붙인다(F-WEB-05, F-RES-04). 페이지 속 문장이 다른 행동을 요구해도 따르지 않는다(F-WEB-06).

### 흐름 3. 반복 작업 등록과 알림(출석 포함)

1. 사용자가 "○○앱 출석체크 매일 밤 9시에 알려 줘"라고 입력한다.
2. 서버가 반복·알림 작업으로 해석하고 계획 카드 대신 반복 설정 시트(SCR-H06)를 보여 준다. 시트에는 "알림을 드리고, 출석은 직접 해 주세요"를 명시한다(01 §6.2).
3. 사용자가 시각·요일을 확인하고 저장한다. 작업함 "반복" 묶음에 등록된다(F-ROUT-02).
4. 매일 21:00에 마감 알림을 보낸다(F-ROUT-01). 알림을 누르면 해당 앱 딥링크나 사이트를 연다.
5. Phase 2부터는 알림에서 "콜비로 열기"를 고르면 웹 작업 화면에서 출석 버튼까지 처리하는 "지켜보는 한 번 실행"을 쓴다(F-ROUT-03). 로그인은 손 넘기기로, Captcha는 사용자가 푼다.
6. 반복 전화(SC-10)는 실행 전 알림 → 사용자 승인 → 발신 순서다. 승인이 없으면 그 회차를 건너뛰고 기록한다(F-ROUT-04, C-8).
7. 사용자는 SCR-T07에서 일시정지·삭제·시각 변경을 한다. 연속으로 3회 이상 반응하지 않으면 "계속 알려 드릴까요?"를 묻는다(가정: 알림 피로 방지 규칙).

### 흐름 4. 연동 연결(OAuth) 온보딩

연동은 첫 실행에서 한꺼번에 묻지 않고, 그 기능을 처음 쓰는 순간에 요청한다(02 §5 P24).

1. 사용자가 결과 카드에서 [캘린더에 추가]를 처음 누른다.
2. 사전 안내 시트: "일정을 넣으려면 캘린더 접근이 필요해요" + 선택지 [이 휴대폰 캘린더] / [Google 캘린더 연결](Phase 2). 버튼 하나의 원칙은 선택지마다 지킨다.
3. 기기 캘린더를 고르면 OS 권한 창을 띄운다. 거부하면 [일정 파일 저장](F-INTG-01)으로 대신하고 설정에서 다시 켜는 방법을 알린다.
4. Google 캘린더를 고르면 OAuth 화면으로 넘긴다. 요청 범위는 일정 읽기·쓰기로 한정하고, 화면에 "무엇을 읽고 무엇을 쓰는지"를 먼저 적는다(로드맵 §4.4 최소 범위).
5. 연결이 끝나면 원래 화면(확인 시트)으로 돌아와 일정을 보여 주고, 사용자가 [추가]를 누를 때 쓴다(C-7).
6. 연결 상태와 해제는 내 정보 > 연결한 앱(SCR-M04)에서 관리한다. 해제하면 서버의 토큰을 즉시 폐기한다.
7. Gmail 연결(Phase 2)도 같은 방식이다. 처음 "메일에서 일정 찾아 줘"를 할 때 범위(기간·발신자)를 고르게 하고 읽기 범위만 요청한다.

### 흐름 5. 첫 실행 온보딩

1. 온보딩 1장: 콜비가 할 수 있는 일(전화로 예약·문의·변경, 결과 정리, 일정·지도 연결)과 못 하는 일(결제 정보 입력, 비밀번호 보관, 자동 출석)(02 §8.3 S9, 02 §4.4 HAX G1).
2. 온보딩 2장: 약속 — "통화할 때 AI임을 먼저 밝혀요", "돈·약정·제출은 꼭 먼저 물어요", "대화는 글로 기록되고, 언제든 지울 수 있어요". AI 사전 고지(F-TRUST-02)와 첫 통화 신뢰 안내를 이 장으로 합쳐 확인을 한 번으로 줄인다(02 §7.2 C5).
3. 로그인(SCR-O04): 소셜 로그인 → 휴대폰 번호 확인(F-ACCT-01·06). 약관·개인정보 처리 동의.
4. 온보딩 3장: 예약자명으로 쓸 이름 입력(F-MEM-05). 회신 번호는 확인한 휴대폰 번호를 기본값으로 제안한다.
5. 홈으로 이동. 빈 상태는 "할 수 있는 일 3가지 예시 + 입력칸"이다(02 §5 P26). 알림·위치·연락처·마이크 권한은 이 단계에서 묻지 않는다.

### 흐름 6. 앱 밖에서 승인 요청 받기

1. 통화 중 승인이 필요해지면 서버가 승인 요청을 만들고, 사용자의 앱이 열려 있지 않으면 긴급 알림을 보낸다(F-NOTI-02). 알림 본문은 잠금 화면에 보여도 되는 수준으로 쓴다("라 파스타 통화에서 확인할 일이 있어요"). 금액 같은 세부는 앱 안에서만 보인다(02 §4.1 Live Activities 민감 정보 원칙을 알림에도 적용, 가정).
2. 잠금 화면 진행 표시도 "확인 필요" 단계로 바뀐다.
3. 사용자가 알림을 누르면 작업 상세의 승인 카드가 펼쳐진 채로 열린다. 남은 시간은 서버 기준 만료 시각으로 다시 계산한다.
4. [승인]·[거절]·칩·코멘트로 답한다. 알림 액션의 [거절]은 바로 보낼 수 있다(F-APPR-08, Phase 2).
5. 만료되면 거절로 처리하고 알림을 "시간이 지나 진행하지 않았어요"로 바꾼다.

### 흐름 7. 메일 속 일정 캘린더 등록(Phase 2)

1. "이번 달 학교 메일 일정 캘린더에 넣어 줘" 입력.
2. Gmail이 연결되어 있지 않으면 흐름 4로 연결한다.
3. 계획 카드에 읽을 범위(기간, 발신자·키워드)를 보여 주고 확인받는다.
4. 서버가 범위 안 메일에서 일정 후보를 뽑는다. 메일 속 문장은 지시로 따르지 않는다(F-WEB-06과 같은 규칙).
5. 결과 카드에 일정 후보 목록을 보여 준다. 시간이 불분명한 항목은 "확인 못 함"으로 표시한다. 연결된 캘린더와 겹치는 일정은 표시한다(F-INTG-09).
6. 사용자가 추가할 항목을 골라 [캘린더에 추가]를 누르면 쓴다(C-7). 메일 본문은 결과 생성 뒤 보관하지 않는다.

## 7. 작업(Task) 모델

### 7.1 작업 종류

| `kind` | 의미 | 실행 수단 | 예 |
|---|---|---|---|
| `call` | 전화로 목적을 달성 | KAT 발신 + 음성 AI | 예약, 문의, 변경, 협상 |
| `web` | 웹 페이지에서 목적을 달성 | 기기 안 브라우저(기본), 서버 원격 브라우저(공개 페이지 한정) | 양식 작성, 출석 한 번 실행 |
| `reminder` | 정해진 시각에 알리고 바로가기를 준다 | 푸시, 딥링크 | 출석 마감 알림, 쿠폰 만료 |
| `integration_action` | 연결한 앱을 읽거나 쓴다 | 기기 API 또는 OAuth 연동 | 캘린더 추가, 메일에서 일정 찾기 |

- 한 부탁이 여러 작업으로 나뉠 수 있다. 예: "여러 곳 비교"는 부모 작업 하나와 `call` 하위 작업 여러 개, 결과 카드의 "캘린더에 추가"는 `integration_action` 하위 작업이다. 작업함에는 부모 작업만 보인다.
- 반복은 작업 종류가 아니라 **`Routine`(반복 정의)**이다. `Routine`이 회차마다 작업을 만든다.

### 7.2 상태

목표 상태 목록(모든 종류 공통):

| 상태 | 의미 | 사용자 화면 묶음 |
|---|---|---|
| `planning` | 계획을 세우는 중 | 진행 중 |
| `awaiting_confirmation` | 계획 카드 확인 대기(현재 `awaiting_approval`) | 내 차례 |
| `scheduled` | 정해진 시각을 기다리는 중 | 반복 / 진행 중 |
| `running` | 실행 중. 세부 단계는 `phase`로 표현 | 진행 중 |
| `waiting_user` | 실행 도중 사용자 응답 대기. 무엇을 기다리는지는 `pendingAction`(§7.3) | 내 차례 |
| `summarizing` | 결과 정리 중 | 진행 중 |
| `completed` | 끝남. 결과는 `outcome.result`(success / partial / failed / unverified) | 끝남 |
| `failed` | 실행 자체가 실패(연결 실패, 시스템 오류) | 끝남 |
| `canceled` | 사용자가 취소 | 끝남 |
| `skipped` | 반복 회차가 승인 없이 지나감 | 반복(이력) |

`phase` 값:

| `kind` | `phase` |
|---|---|
| `call` | `dialing` → `ringing` → `in_call`(현재 `in_progress`) → `ivr`(ARS 탐색, Phase 2) → `on_hold`(대기, Phase 3) |
| `web` | `opening` → `acting` → `paused`(사용자가 앱을 떠남) |
| `reminder` | `notified` |
| `integration_action` | `reading` / `writing` |

주요 전이:

```
planning ──► awaiting_confirmation ──► running ──► summarizing ──► completed
   │               │      │               │  ▲            │
   │               │      └► scheduled ───┘  │            └► failed
   │               │                         │
   │               │          running ◄──► waiting_user (승인·손 넘기기·제출 확인)
   │               │
   └──► failed     └──► canceled  (planning·awaiting_confirmation·scheduled·running·waiting_user 어디서나 사용자 취소 가능)

L2(알아서 하기): planning ──► running (awaiting_confirmation 생략, 저위험 조건 충족 시에만)
reminder:        scheduled ──► running(phase=notified) ──► completed
Routine 회차:    scheduled ──► waiting_user(run_confirm) ──► running | skipped
```

규칙:

- `waiting_user`에서 만료되면 `pendingAction`의 기본값으로 처리한다. 승인 계열은 거절로 보고 `running`으로 돌아가 AI가 정리한다. 손 넘기기는 작업을 멈추고 `waiting_user`에 남기거나(웹), 정해진 시간 뒤 `canceled`로 끝낸다(§14 OD-6과 함께 확정).
- `running`에서 시스템 종료·배포가 일어나면 진행 중 통화를 끊고 `failed`로 기록한다(OPERATIONS 종료 절차 유지). 기동 복구는 어떤 작업도 새로 발신하지 않는다(EPIC D3).
- 모든 변경은 `version`을 올린다(현재 규칙 유지).

### 7.3 승인 종류(`pendingAction.kind`)

| 종류 | 언제 | 사용자 응답 | 만료 시 | 관련 기능 |
|---|---|---|---|---|
| `plan_confirm` | 실행 전 계획 확인 | 시작 / 고치기 / 취소 | 실행 안 함(작업 유지) | F-APPR-01 |
| `decision` | 실행 중 예/아니오 결정 | 승인 / 거절 + 코멘트 | 거절 | F-APPR-02·03 |
| `spend_cap` | 금액이 걸린 결정 | 상한 선택("N원까지") 또는 거절 | 거절 | F-APPR-04 |
| `submit` | 제출·발송·게시·예약 확정(웹) | 사용자가 직접 마지막 버튼 | 실행 안 함 | F-APPR-07 |
| `handoff` | 로그인·결제 정보·Captcha·본인 인증 | 사용자 직접 조작 후 [이어서] | 멈춤 후 취소 | F-APPR-06 |
| `write` | 연결한 앱에 쓰기 | 추가 / 고치기 / 취소 | 쓰지 않음 | F-INTG-02·03 |
| `run_confirm` | 반복 회차 실행 | 실행 / 이번만 건너뛰기 | `skipped` | F-ROUT-04 |

모든 승인은 작업별·회차별로 따로 받는다(C 보조 규칙). 응답은 감사 기록에 남긴다(F-TRUST-07).

### 7.4 결과 형식

현재 `CallOutcome`을 일반화한 `TaskOutcome`:

| 필드 | 설명 | 현재 |
|---|---|---|
| `result` | `success` / `partial` / `failed` / `unverified` | 있음 |
| `source` | `llm` / `heuristic` / `evidence`(상대 확정 증거로 올림, Phase 3) | `llm`·`heuristic` |
| `summary` | 한두 문장 요약 | 있음 |
| `keyFacts` | 확인된 사실 목록 | 있음 |
| `unconfirmed` | 확인 못 한 항목 목록(결과 카드 "확인 못 한 것") | 없음(신규) |
| `followUps` | 사용자가 할 일 | 있음 |
| `appointment` | 확정된 일정(LLM success·partial에만) | 있음 |
| `evidence[]` | `transcript_excerpt` / `screenshot` / `confirmation_code` / `shared_message` | 없음(신규) |
| `comparison` | 여러 곳 비교표(부모 작업만) | 없음(신규) |
| `suggestedActions` | 주 행동 1 + 보조 3(서버가 순서 제안, 앱이 표시) | 앱이 계산(현재) |

### 7.5 현재 서버 상태 머신과의 차이

현재: `server/src/domain/types.ts`의 `TaskStatus`, `server/src/domain/stateMachine.ts`.

| 항목 | 현재 | 목표 | 바꾸는 이유 |
|---|---|---|---|
| 작업 종류 | 전화뿐(`CallTask`) | `kind`: call / web / reminder / integration_action | 웹·알림·연동 수용(02 §7.2 C2) |
| 계획 확인 상태 | `awaiting_approval` | `awaiting_confirmation` | 통화 중 승인(`approvals`)과 이름이 겹쳐 혼동 |
| 실행 상태 | `dialing`, `ringing`, `in_progress`가 최상위 상태 | `running` + `phase` | 종류마다 다른 세부 단계를 상태 폭증 없이 표현 |
| 사용자 대기 | 상태가 아니다. `in_progress` 중 `approvals[]`에 `pending` 항목 | `waiting_user` + `pendingAction` | 작업함 "내 차례" 묶음·배지·알림의 기준이 상태 하나로 정해짐 |
| 승인 종류 | 예/아니오 + 코멘트 한 가지 | 7종(§7.3) | 금액 상한, 손 넘기기, 제출, 쓰기, 반복 실행 |
| 예약 실행 | 없음 | `scheduled`, `Routine` | 예약 통화, 반복, 알림 |
| 건너뜀 | 없음 | `skipped` | 반복 회차 승인 없음 |
| 자동 시작 | `autoStart` 플래그로 `awaiting_approval` → `dialing` | 같은 동작을 `awaiting_confirmation` → `running`으로. L2는 `planning` → `running` | 기존 순서(503 → 404 → 409 → 400 → 429, EPIC D3) 유지 |
| 결과 | `CallOutcome` | `TaskOutcome`(§7.4) | 증거·확인 못 한 항목·비교 |
| 소유자 | 없음(공유 `API_TOKEN`) | `userId` 필수 | 계정·푸시·데이터 분리(F-ACCT-02) |
| 저장소 | 단일 JSON 파일, 단일 인스턴스 | 사용자별로 분리된 공유 저장소, 다중 인스턴스 | Phase 0(§11) |
| 호환 | — | 기존 저장 작업은 `kind=call`로 읽고 상태를 대응표로 바꿔 읽는다. 서버·앱 동시 배포 원칙 유지(EPIC D1, OPERATIONS) | 과거 기록 보존 |

### 8.2 지도 열기 — 딥링크

- 장소 상세·결과 카드의 [길찾기]는 사용자가 고른 기본 지도 앱(카카오맵, 네이버지도, Apple 지도, Google 지도)으로 목적지(이름·좌표)를 넘긴다. 앱이 없으면 웹 지도로 연다.
- 앱 안에 지도를 그리지 않는다(Phase 1). 지도를 그리면 제공자별 표시 의무가 생긴다(Google의 경우 01 §5.2).
- 각 지도 앱의 공개 URL 스킴과 파라미터는 구현 전에 공식 문서로 확인한다(이 문서의 입력 자료에는 없음).

### 8.5 브라우저 실행 방식 — 서버 원격 브라우저 vs 기기 안 WebView

| 기준 | 서버 측 원격 브라우저 | 기기 안 WebView |
|---|---|---|
| 참고 사례 | Gemini 원격 브라우저(기기를 닫아도 계속), ChatGPT 가상 브라우저 넘겨받기(01 §3.3) | Gemini의 로컬 Chrome(사용자 로그인 그대로 사용, 01 §3.3) |
| 로그인 세션 위치 | 콜비 서버에 쿠키가 남는다. 보관 기간·삭제 버튼 필수(01 §6.3) | 사용자 기기에만 남는다 |
| 손 넘기기 | 원격 화면을 스트리밍해 사용자가 조작. 지연과 입력 불편, 본인 인증 앱 전환이 어려울 수 있음(가정) | 같은 화면에서 바로 넘긴다. 본인 인증 앱 전환이 자연스러움(가정) |
| 약관 위험 | 서버 IP에서 사용자 계정으로 접속 → "사람의 실제 이용 전제" 조항과 충돌 가능성이 더 큼(01 §6.2) | 사용자가 보는 화면, 사용자 기기·IP. 그래도 AI가 클릭하는 자동화라 **법률·약관 검토 필요** |
| 사용자가 없을 때 실행 | 가능(그래서 위험, 01 §3.3 Gemini 경고) | 앱이 열려 있어야 함(지켜보는 실행이 강제됨) |
| 보안 | 서버가 다수 사용자의 세션을 보관 → 유출 시 피해 큼. 격리·감사 필요 | 세션이 분산되어 집중 위험 낮음. 기기 탈취 위험은 OS에 의존 |
| 비용·운영 | 브라우저 인스턴스 비용, 스케일링 부담(가정) | 서버 비용 낮음. 기기 성능·OS별 WebView 차이 대응 필요(가정) |
| 화면 이해 | 서버에서 스크린숏·DOM을 바로 얻음 | 앱이 스크린숏·DOM을 추출해 서버 모델로 보냄. 손 넘기기 중에는 전송 중지 |

**권고: 기기 안 WebView를 기본 실행 방식으로 한다.** 로그인이 필요한 작업과 출석 "한 번 실행"은 모두 기기 안에서 사용자가 지켜볼 때만 진행한다. 서버 원격 브라우저는 Phase 3에 로그인이 필요 없는 공개 페이지 조회(F-WEB-08)에만 쓴다. 근거: 자격 증명·세션을 콜비 서버에 두지 않는다는 약속(§2.2), 약관 위험 축소(01 §6.2), 지켜보기 모드가 구조적으로 강제됨(02 §5 P16). 최종 결정은 §14 OD-3.

보안 공통 규칙: 허용 사이트 목록(F-WEB-02), 금융 등 고위험 범주 차단(01 §6.3), 페이지 내용을 지시로 취급하지 않기(F-WEB-06), 손 넘기기 중 화면 전송·기록 중지(02 §5 P15), 자격 증명은 볼트 연동 후보로만 검토(01 §6.3 1Password 사례, Phase 3 이후).

### 9.3 비용 — 모두 가정

실제 단가는 KAT·OpenAI·푸시·호스팅 계약과 실측으로 정한다. 이 절의 숫자는 요금제 설계를 위한 **가정**이다.

| 항목 | 가정 | 비고 |
|---|---|---|
| 통화 1건 평균 길이 | 3분(가정) | 02 §5 P8의 "보통 3~5분" 안내 예시와 맞춤. 출시 전 실측으로 교체 |

## 10. 요금제·수익 모델 후보

모든 금액·한도는 **가정**이다. 단가 확정(§9.3) 뒤 다시 계산한다. 참고로 Meta Muse는 미국에서 월 $20부터의 유료 구독으로 업체 통화를 제공한다(01 §3.2). 국내 통신사 기능의 요금은 확인되지 않았다(01 §8 U12).

| 항목 | A. 무료 한도 + 월 구독 | B. 건당 과금(크레딧) | C. 혼합(무료 한도 + 구독 + 추가 크레딧) |
|---|---|---|---|
| 무료 | 월 3건 작업(가정) | 가입 시 크레딧 3건(가정) | 월 3건(가정) |
| 유료 | 월 9,900원에 월 30건(가정) | 1건 990원, 10건 묶음 7,900원(가정) | 월 9,900원 30건 + 초과 시 건당 990원(가정) |
| 무엇을 1건으로 세나 | 전화 1통(통화 3분 기준, 넘으면 분당 추가 차감, 가정). 알림·캘린더 추가는 세지 않음 | 같음 | 같음 |
| 장점 | 예측 가능한 매출, 반복 사용 유도 | 가끔 쓰는 사용자 부담이 낮음 | 두 사용자 집단 모두 수용 |
| 단점 | 가끔 쓰는 사용자는 가입하지 않음 | 매출 변동, 매번 비용 의식 → 사용 억제 | 요금 설명이 복잡해짐(02 §3.10 토스 Simple Policy) |
| 실패 처리 | 연결 안 됨·AI 거절·확인 못 함은 차감하지 않거나 절반 차감(가정, §14 OD-4) | 같음 | 같음 |

**권장: 출시(Phase 1)는 무료 한도만 운영해 성공률·원가를 실측하고, Phase 2에서 A안(무료 한도 + 월 구독)으로 유료화한다. C안은 초과 사용 데이터가 쌓인 뒤 검토한다.** 근거: 요금 정책이 단순해야 화면도 단순하다(02 §3.10), 실패 통화 비율(01 §1-8)을 모르는 상태에서 건당 가격을 정하면 손실 위험이 크다. 최종 결정은 §14 OD-4.

## 11. 단계별 로드맵

시간 예측 대신 순서와 출시 기준으로 표현한다. 각 단계는 앞 단계의 출시 기준을 모두 충족한 뒤 시작한다. 지표 목표값은 모두 가정이며, Phase 0 동안 측정 방식을 먼저 갖춘다.

### Phase 0 — 상용 배포 선행 과제

- **목표**: 개발용 단일 서버 구조를 여러 사용자가 동시에 쓰는 상용 구조로 바꾼다. 사용자에게 보이는 기능은 거의 늘지 않는다.
- **포함 기능**: F-ACCT-01·02·05·06, F-NOTI-01, F-INBOX-05, F-TRUST-02·03, F-SET-06
- **포함 기술 과제**:
  1. 사용자 계정과 사용자별 인증으로 공유 `API_TOKEN` 대체(product.md, EPIC §6).
  2. 저장소를 단일 JSON 파일에서 다중 인스턴스가 함께 쓰는 저장소로 전환하고 사용자별로 분리(OPERATIONS "단일 인스턴스", EPIC D10).
  3. 통화 세션 소유와 승인 응답 전달 경로 설계(NFR-AVL-02), 진행 중 통화를 보호하는 배포 절차(NFR-AVL-01).
  4. 기기 등록과 푸시 발송 기반(F-NOTI-01).
  5. 작업 모델 전환 준비: `kind`·`userId`·`waiting_user` 도입과 기존 기록 읽기 호환(§7.5).
  6. 번호 정규화 잔여 위험 정리(`119-1234-5678` 같은 사례, 대표번호 처리, OPERATIONS 잔여 위험, EPIC §6).
  7. 상용 빌드에서 개발용 설정 제거, 앱 이름 결정 반영(§14 OD-12).
  8. 법률 검토 착수: NFR-LAW-01~05·08 질의서 송부.
  9. 측정 기반: 작업 이벤트 수집(§12 지표), 비용 집계.
- **선행 조건**: 소유자 결정 OD-1(고지·녹음 방침의 잠정안), OD-9(로그인 수단), OD-12(앱 이름).
- **출시 기준(내부 베타 개방 조건)**:
  - 사용자 간 데이터 접근 차단 테스트 100% 통과.
  - 인스턴스 2개 이상에서 통화 중 승인 왕복 성공률 99% 이상(내부 시험 100건, 가정).
  - 테스트 기기 푸시 도달률 95% 이상(가정).
  - 진행 중 통화가 있는 상태에서 배포해도 끊긴 통화 0건.
  - 법률 검토 1차 의견 수령(고지·녹음·자동 발신).

- **검토 후보(이 문서의 기능 목록에 넣지 않음)**: 수신 대행(로드맵 §4.3 P2. 통신사·카카오가 녹음·요약을 무료 제공하는 영역이라 경쟁 이득이 작음, 01 §7.3-5), 장소 탭(02 §8.2 C안), 카카오 PlayMCP·네이버 Agent N 연결(01 §8 U13·U14), 허브 플랫폼·SDK(product.md 목표 방향).
- **선행 조건**: Phase 2 출시 기준 충족, 제휴 협의 결과, 통화 넘겨받기·대기 기능에 대한 KAT 기능 확인.
- **출시 기준(목표값은 가정)**: 기능별로 Phase 2와 같은 형식(완료율, 승인 없는 고위험 행동 0건, 원가 목표 충족)을 기능 착수 시 정한다.

## 12. 성공 지표

### 12.1 북극성 지표

**주간 "끝난 부탁" 수**: 한 주 동안 결과가 `success` 또는 `partial`로 끝나고 사용자가 결과를 확인한 작업 수(부모 작업 기준).

- 이유: 콜비의 가치는 "일을 끝내 주는 것"이다. 작업 시작 수는 실패를 포함하고, 활성 사용자 수는 가치를 직접 재지 않는다. "확인 못 함"을 빼서 확정되지 않은 결과를 성공으로 세지 않는다(EPIC D5와 같은 원칙).
- 측정: 서버 작업 이벤트(`completed` + `outcome.result`)와 앱의 결과 화면 열람 이벤트를 결합.

### 12.2 보조 지표

| 영역 | 지표 | 정의 | 측정 방법 |
|---|---|---|---|
