# CallMate 제품 고도화 검토 및 단계별 구현 계획

> 기준 문서: `PRODUCT_ROADMAP(1).md`, `ARCHITECTURE.md` (2026-11-20 제공본)  
> 상태: **설계 제안 / 실제 소스코드 미검증**. 파일 경로와 구현 상태는 제공된 아키텍처 문서의 기술을 근거로 하며 Cursor가 실제 저장소와 대조해야 한다.

## 1. Executive decision

**핵심 원칙:** 현재 Flutter + Fastify/TypeScript + KAT Cloud + OpenAI Realtime 시스템을 교체하지 않는다. 통화 핵심 기능을 안정화한 다음, 사용자 승인·재사용 UX·알림을 우선 개선하고, 커넥터/계정/멀티채널 업무 엔진을 단계적으로 추가한다.

- 단기 제품 가치: **승인 코멘트 → 최근 상대/템플릿 → 푸시 → 입력 편의 → 통화 후 액션**.
- 플랫폼 확장 준비: 초기부터 **승인 권한 판정, idempotency, 상태 버전, 이벤트/감사 기록**을 추가하되, 범용 워크플로 엔진을 지금부터 과도하게 개발하지 않는다.
- 서버는 authoritative state를 유지한다. Flutter는 화면·입력·로컬 선택만 담당한다.
- 실제 결제나 약정은 LLM의 프롬프트가 아닌 **서버 측 정책과 수동 승인**이 필수다. 승인 코멘트가 새 조건을 추가할 경우 이를 실행 권한 확대의 근거로 해석하지 않는다.

## 2. 제공 문서 대비 주요 검토 의견

| 구분 | 확인된 현행 설계 | 개선/결정 | 이유 |
|---|---|---|---|
| 서버/클라이언트 | Flutter Riverpod, Fastify REST+WebSocket, full snapshot + `version` | 유지 | 기존 장점인 순서 역전 복구와 점진 도입 보존 |
| 전화 | `CallProvider` (simulated/KAT), `CallBrain` (OpenAI/heuristic) | 유지 + 계약 회귀 테스트 | 실통화와 시뮬레이터 동작 일관성 |
| 승인 | `boolean` 응답, 승인/거절, 타임아웃 시 거절 | `ApprovalDecision` 객체, 댓글 500자, 원자적 결정 | 통화 중 조건 전달/경합 처리 |
| 백그라운드 | 푸시 부재 | APNs/FCM + 앱 복귀 후 서버 최신 상태 재조회 | 푸시는 전달 보장이 아닌 알림 채널 |
| 저장 | TaskStore JSON + 메모리 | Phase A는 유지, 지속성/경합 검증. B에서 RDBMS 전환 | 즉시 DB 변경 시 위험 상승 |
| 인증 | 옵션 `API_TOKEN`, 실통화 강제 | 개인 사용 PoC에서는 유지, 다중 사용자 전 OAuth/OIDC 계정 및 owner check 필수 | 공용 API 토큰은 다중 사용자 보안 경계가 아님 |
| 보안 | AI 고지, 민감정보 프롬프트, KAT 서명 | 강제 정책 검사, 비밀 마스킹, 감사 이벤트, 통합 승인 거부 규칙 | 프롬프트만으로 통제 불가 |
| AgentTask | 현재 `CallTask`는 통화와 업무가 사실상 동일 | Phase B 후반에 `AgentTask`/`CallSession` 분리 도입 | 복수 채널/재시도/예약 통화 지원 |
| 커넥터 | 로드맵의 개념 설계 | API 서버 전용 OAuth 토큰과 capability별 authorization | 외부 서비스 권한 오남용 방지 |
| 수신 대행 | P2 아이디어 | KAT 기능·번호 소유권·포워딩·법률 검토 후 별도 PoC | 발신 구조를 단순 재사용할 수 있다고 가정 금지 |

### 문서 간 일정 및 우선순위 충돌

1. 제품 로드맵은 계정 동기화를 P1에 배치하고, 기존 아키텍처 기술 백로그는 3단계(상대적으로 이른 시점)에 배치한다. **권장:** 단일 사용자 PoC의 Phase A는 기존 보안 경계를 유지하되, 타인/다중 기기 지원 또는 커넥터 OAuth를 정식 공개하기 **전에** 계정/소유권/DB 기반을 반드시 완성한다.
2. 제품 로드맵 Phase A는 템플릿을 푸시보다 먼저 구현하자는 실행 제안을 포함한다. **권장:** 승인 코멘트 이후 템플릿과 푸시는 독립 브랜치로 병렬 진행 가능하나 실제 릴리스 게이트는 승인 알림 신뢰도를 우선한다.
3. 기존 문서의 `CallTask`가 완료된 통화와 개인 비서의 범용 업무를 모두 나타내기에는 한계가 있다. **권장:** 당장 기존 API를 개명하지 말고 AgentTask를 신규 리소스로 점진 추가한다.
4. `WebSocket ?token=` 인증은 기존 설계에 기술되어 있지만 브라우저/프록시 로그 노출 위험이 있다. **권장:** 기존 호환은 유지하되 단기 토큰/인증 헤더가 가능한 채널로 점진 이전하고 쿼리 토큰은 제거 시점을 정한다.

## 3. 단계별 개발 계획 (예상 기간은 추정치; 팀·환경에 따라 변동)

| 단계 | 범위 | 선행 조건 | 주요 산출물 | 종료 기준 | 예시 기간 |
|---|---|---|---|---|---|
| 0. Baseline | 저장소 확인, 테스트, 시뮬레이터/실통화 계약 점검 | 저장소, 테스트 키 | 현황 보고서, 테스트/CI, 회귀 시나리오 | 기존 기능 전부 통과, 위험 목록 확정 | 3–5일 |
| A1 | 승인 코멘트와 서버 정책 | 0 | API/도메인/앱/Realtime 수정 | 승인/거절/만료/중복/재접속 테스트 통과 | 4–7일 |
| A2 | 최근 상대/템플릿, 재통화 | A1 또는 병렬 | 로컬 목록·템플릿 UX | 민감정보 자동 복원 없음, 재실행 시 계획 재검토 | 4–7일 |
| A3 | 푸시 승인·종료·실패 | A1, 모바일 설정 | 토큰 등록, 알림 워커, 딥링크 | 알림 클릭 시 최신 승인 상태, 만료된 승인 실행 불가 | 5–10일 |
| A4 | 연락처 선택, STT 입력 | 0 | 권한 UI/선택된 연락처만 전송/STT | 전체 주소록 업로드 없음, 권한 거부 동작 | 4–8일 |
| A5 | 후속 액션/신뢰 UX | A1 | 캘린더 초안, 복사/공유, 고지 | 외부 쓰기 전에 사용자 최종 확인 | 3–6일 |
| B0 | 계정/소유권/Postgres | A 안정화 | Auth, RDBMS, 마이그레이션 | 사용자 간 리소스 접근 차단, 재시작/복구 테스트 | 2–4주 |
| B1 | 커넥터 기반과 Calendar | B0 | registry, OAuth, 최소 권한, Calendar | 연결 해제·토큰 폐기/갱신·쓰기 승인 테스트 | 2–4주 |
| B2 | 국내 업체 검색, 예약 통화, ARS | B0/B1 일부 | 탐색·스케줄러·DTMF | 예약 중복 방지, 공급자 기능 확인 | 3–6주 |
| C1 | AgentTask/오케스트레이션·채팅 홈 | B 안정화 | 다단계 업무 모델·UI | 다중 통화/커넥터 단계 재실행/취소 | 4–8주 |
| C2 | 음성/카메라 OCR/메모리 | C1 | 동의·수정·삭제 UI | 목적 제한, 접근제어, 삭제 검증 | 4–8주 |
| C3 | 인바운드 대행·웹/결제 PoC | 별도 외부 검증 | 기술·법적 PoC | 번호·사업자·고지·승인 조건 충족 | 별도 산정 |

**기간 해석:** 작업 난도별 대략치이며 총 일정 확정값이 아니다. 일정 확정 전에 개발자 수, iOS/Android 배포 계정, 푸시/클라우드 인프라와 KAT 권한을 확인해야 한다.

## 4. 단계별 상세 백로그

### Phase 0: 저장소 Baseline
- `server/src` 및 `app/lib` 실제 디렉터리·의존성·테스트 커맨드 파악.
- 모델/서버/앱 계약 비교 및 `/v1/tasks`, `/v1/stream` 스냅샷+version 회귀 테스트.
- 시뮬레이터 자동화: 계획→발신→승인/거절→종료→요약. 민감정보·금지번호·한도·서버 재시작 테스트.
- KAT 실통화는 키·한국 IP·공개 WSS가 갖춰진 환경에서 **명시적 승인 후에만** 실행; 테스트 비용/실발신 주의.

### Phase A1: 승인 코멘트
- 백엔드 `comment?: string` (trim, 0~500자; 저장 시 원문 안전 처리), `decision` enum.
- 승인 대기 요청은 `pending → approved|rejected|expired|canceled` 중 한 번만 전이. 승인 만료는 거절 의미, 변경 불가.
- 서버 API가 인증/소유권(현재 단계의 API_TOKEN 범위)/task 일치/타임아웃/멱등성 검사.
- `CallSession.requestApproval`의 반환을 `{ approved:boolean, comment?:string, reason?:string }` 형태로 확장; 실제 명칭은 기존 인터페이스에 맞춰 조정.
- Realtime 도구 결과에 `user_comment`와 시스템 결정 사유 포함; **추가 코멘트가 기존 금지 정책보다 우선하지 않음**. 부적절한 조건은 수행하지 말고 재승인을 요청.
- 앱 `ApprovalCard`: 다중 라인 입력, 최대 글자 수, 제출 로딩, 409/만료 안내, 거절+코멘트, 종료 화면 코멘트 표기.

### Phase A2: 최근 상대/템플릿
- 저장 위치는 최초엔 사용자의 로컬 안전 저장소(민감한 내용은 일반 SharedPreferences 저장 피함).
- 템플릿은 상대·전화번호·goal·허용 가능한 context 중 **비민감 값**만 저장. 이전 승인 결과·결제 정보·인증 정보는 복제 금지.
- 재호출은 항상 새 `CallTask` 생성 및 계획 재검토.

### Phase A3: 푸시
- 기기 토큰 수명/갱신/로그아웃 시 삭제, 사용자별 토큰 바인딩 정책을 먼저 정의.
- `approval_requested`, `call_completed`, `call_failed` 이벤트와 알림 dispatch 분리.
- 알림 본문에 민감한 내용/전화번호 전체 노출 금지. 알림의 기한은 **서버**가 정함.
- 딥링크에서 앱 실행 후 GET 최신 상태로 확인. 앱 밖에서 바로 승인하는 액션은 초기에는 금지.
- 개발 PoC의 공용 API_TOKEN과 다중 사용자 푸시를 혼용하지 않는다.

### Phase A4/A5: 편의 및 신뢰
- 연락처는 OS Picker에서 **선택한 1건**만 처리, 선택 화면에서 E.164 변환 확인.
- 음성 입력은 통화 오디오와 별도; STT 오류 시 수정 가능.
- 후속 액션은 OS 공유/캘린더 생성 **초안** 형태로 시작.
- 고지 문구, 자막 보관/삭제, 연결 끊김, 재연결 시 상태 표시를 검증.

### Phase B: 계정/커넥터
- `TaskStore` 추상화를 유지한 Postgres 구현 및 owner scoping; migration/rollback 준비.
- 외부 커넥터 토큰은 서버 내 암호화 저장·회전·폐기/최소 OAuth scopes 적용.
- `read`는 요청 범위 내, `write`는 정책 체크 및 승인, `payment`는 초기 구현 제외.
- 예약 통화의 중복 실행 방지, 스케줄러 재기동 복구, 전화망 요금/동시성 한도.

### Phase C: 멀티채널 업무 엔진
- 새 AgentTask는 계획/단계/승인/실행 결과를 소유. `CallSession`은 전화 1회 실행만 담당.
- 외부 쓰기·돈 관련 작업은 재시도 전에 승인/멱등키 정책 확인.
- OCR/메모리는 동의/목적/보관기간/삭제가 기본. 수신은 외부 기능·법률 검증 별도.

## 5. 테스트 및 배포 게이트

| 분류 | 최소 게이트 |
|---|---|
| 기능 | `npm test`/`flutter test` 등 **실제 프로젝트에 존재하는 명령** 통과, 수동 E2E 기록 |
| 승인 안정성 | 승인 응답/만료 경합, 중복 제출, 취소, 잘못된 task/approval ID, 재접속/재시작 |
| 보안 | 미인증 접근 실패, 토큰/전화번호 로그 마스킹, 민감 문자열 불필요 보관 금지 |
| 통화 | 시뮬레이터 end-to-end 통과, KAT 실통화 테스트는 opt-in |
| WebSocket | HTTP/WS 순서 역전 시 `version` 더 최신값 우선, 재연결 최신 상태 복원 |
| 알림 | 푸시 지연·중복·미수신 시에도 서버 승인 기한 유지 |
| 관측성 | taskId/approvalId 기반 추적, 구조화 로그, 승인/알림 전송 통계(민감 본문 미포함) |
| 배포 | feature flag, 환경변수/secret 확인, migration/rollback, 단계별 활성화 |

## 6. 의사결정 필요 사항
- 계정 인증 방식(OIDC 공급자), 데이터베이스 및 배포 환경, 개인정보 보관 정책.
- APNs/FCM 앱 식별자 및 배포 계정, 개발/운영 기기 구분.
- KAT 추가 API 기능(DTMF, 인바운드, hold, transfer) 실제 지원 범위.
- 캘린더/업체 검색 공급자 이용 조건과 저장·전송 동의 방식.
- 녹음·자막·AI 고지·대리 수행과 통신 관련 한국 법률/사업자 약관에 대한 전문 검토.

## 7. Cursor 작업 원칙
1. **실제 코드 조사 → 변경 영향 분석 → 최소 구현 → 테스트 → 문서 갱신** 순서를 지킨다.
2. 문서의 클래스·파일명이 실제 저장소와 다르면 실제 코드를 우선하고 차이를 보고한다.
3. 한 번에 한 단계만 구현한다. 실행 커맨드·테스트 결과·파일별 변경 요약을 제출한다.
4. 외부 계정 연결, 실제 통화, 결제, 데이터 삭제, 프로덕션 배포는 사용자 승인 없이 수행하지 않는다.
5. 기능이 미구현/검증 불가이면 작동하는 것처럼 보고하지 않고 blocker를 기록한다.
